# plus/ — всё, что Re:Lad добавляет поверх Mihon

Re:Lad построен на [Mihon](https://github.com/mihonapp/mihon). Чтобы обновления Mihon
вливались без больших конфликтов, наш код живёт отдельно, в этой папке, а в код Mihon
мы встраиваемся только короткими помеченными точками входа.

## Что где лежит

| Путь | Что это |
|---|---|
| `PLAN.md` | План проекта, принятые решения, модули и порядок работы, чек-лист перед выпуском |
| `HOOKS.md` | Все места, где мы меняем файлы Mihon, и зачем |
| `LICENSES.md` | Реестр чужих моделей, шрифтов и библиотек с их лицензиями |
| `app-res/` | Ресурсы Re:Lad (название, иконка, логотип, строки), которые перекрывают ресурсы Mihon |
| `core/` | Модуль `:plus:core`: общая основа для функций Re:Lad (наполняется в модуле M1) |
| `panels/` | Модуль `:plus:panels`: чтение по кадрам (поиск кадров на телефоне, порядок, план приближений) |

Модули функций добавляются сюда же: `plus/vision`, `plus/translate`, `plus/panels` и т. д.
Каждый подключается строкой `include(":plus:…")` в `settings.gradle.kts` (точка входа уже есть).

## Правила

1. **Новый код — только в `plus/`.** Исключение — экраны, которым нужны внутренности
   приложения Mihon: они лежат в `app/src/main/java/plus/…`. Это наши новые файлы,
   с Mihon они не конфликтуют.
2. **Правка файла Mihon — только точка входа.** 1–5 строк, обёрнутых в
   `// PLUS -->` … `// PLUS <--`, и запись в `HOOKS.md`. Логику выносим в свой код.
3. **Схему базы данных Mihon не трогаем.** У Re:Lad будет своя база (модуль M1).
4. **Чужие модели, шрифты и библиотеки** попадают в проект только после записи
   в `LICENSES.md`. Некоммерческие лицензии и код или модели Ultralytics (AGPL) не берём.
5. **Строки интерфейса** с префиксом `plus_`. Нужен как минимум английский вариант
   (`values/`) и русский (`values-ru/`).

## Обновление из Mihon

### Как устроена история

В репозитории Re:Lad нет тысяч коммитов Mihon. Каждая версия Mihon попадает сюда
**одним коммитом** «Import Mihon vX.Y.Z» в отдельной ветке `mihon`:

```
mihon:  Import Mihon v0.21.3 ── Import Mihon v0.21.4 ── …
                 │                       │ (merge)
main:            └── наши коммиты ───────┴── наши коммиты …
```

Git вливает обновления как обычно: общий предок — предыдущий импорт. В последнем
коммите ветки `mihon` есть служебные строки `Mihon-Ref` и `Mihon-Commit` с точной
версией Mihon. По ним работают скрипт импорта и еженедельная проверка.

Полная история Mihon нужна только для импорта. Она скачивается из remote `upstream`
(`https://github.com/mihonapp/mihon`) и живёт только локально. Ветки Mihon лежат
в `upstream/*`, теги — в `upstream/tags/*`, а не среди наших тегов.
**Никогда не делать `git push --tags` и не отправлять ветки `upstream/*`.**

### Как обновиться

Ветка Mihon, за которой мы идём, записана в `plus/upstream.properties` (сейчас `0.21.0`,
позже перейдём на `main`, подробности в `PLAN.md`, раздел 1).

```bash
bash plus/tools/import-mihon.sh            # свежая версия отслеживаемой ветки
bash plus/tools/import-mihon.sh v0.21.4    # или конкретный тег Mihon
```

Скрипт создаёт коммит импорта в `mihon` и вливает его в новую ветку `sync/ГГГГ-ММ-ДД`.
При конфликте в файле из `HOOKS.md` сохраняем смысл нашей правки и переносим её
на новый код Mihon, затем `git commit`. После сборки и проверки:

```bash
git switch main && git merge --ff-only sync/ГГГГ-ММ-ДД && git push origin main mihon
```

Каждый понедельник workflow **Re:Lad upstream check** делает то же самое на пробу,
ничего не отправляя. Если есть что вливать или нашёлся конфликт, он открывает задачу
«Mihon upstream update» (GitHub пришлёт письмо). Запустить проверку вручную:
GitHub → Actions → Re:Lad upstream check → Run workflow.

## Выпуск версии

1. Повысить `versionName` в `plus/version.properties` (например, `0.2.0`) и закоммитить.
2. Поставить тег с тем же номером и приставкой `relad-` и отправить его
   (теги вида `vX.Y.Z` заняты историей Tachiyomi и Mihon):
   ```bash
   git tag -a relad-v0.2.0 -m "Re:Lad v0.2.0" && git push origin relad-v0.2.0
   ```
3. Workflow **Re:Lad release** соберёт и подпишет APK, проверит отпечаток подписи
   и создаст **черновик** выпуска на GitHub с описанием и контрольными суммами.
4. Проверить черновик и нажать «Publish». Только после этого встроенная проверка обновлений
   увидит новую версию.

Для подписи нужны секреты `RELAD_SIGNING_KEY` и `RELAD_KEYSTORE_PASSWORD`
(один раз: `bash plus/tools/upload-signing-secrets.sh`).

## Сборка

```bash
./gradlew :app:assembleDebug
```

Получается пробная сборка `app.relad.dev` («Re:Lad Dev»), которая ставится рядом с Mihon.

## Подпись

Android ставит обновление, только если оно подписано тем же ключом, что и установленная
версия. **Потеря ключа или пароля = Re:Lad больше нельзя обновить** (только удалить
и поставить заново). **Утечка ключа = кто угодно может выпустить поддельное обновление.**

| Что | Где |
|---|---|
| Ключ | `~/.relad/relad-release.jks`, псевдоним `relad`, RSA 4096, срок 10 000 дней |
| Пароль для сборки | `keystore.properties` в корне репозитория (git его игнорирует, права 600). Это встроенный механизм Mihon |
| Ключ на GitHub Actions | Секреты репозитория (настраиваются в M0.6) |
| Отпечаток SHA-256 | В `PLAN.md`, раздел M0.5: по нему проверяют, что APK подписан нами |

Если `keystore.properties` есть, Mihon подписывает этим ключом и пробные, и выпускные сборки.
Если файла нет, сборка подписывается стандартным отладочным ключом Android Studio.

### Создать ключ (один раз)

```bash
bash plus/tools/create-signing-key.sh
```

Скрипт спросит пароль (минимум 16 символов), создаст ключ и `keystore.properties`.
Существующие файлы он не перезаписывает.

### Резервные копии (обязательно, в двух местах)

1. **Менеджер паролей.** Создай запись «Re:Lad signing key». Вложи файл
   `~/.relad/relad-release.jks`, впиши пароль, псевдоним `relad` и отпечаток SHA-256.
2. **Облако, зашифрованный архив.** Создай зашифрованный образ диска с ключом
   (macOS спросит пароль для образа, сохрани его тоже в менеджере паролей):

   ```bash
   hdiutil create -encryption AES-256 -srcfolder ~/.relad -format UDZO ~/Desktop/relad-key-backup.dmg
   ```

   Загрузи `relad-key-backup.dmg` в iCloud Drive или Google Drive и удали его с рабочего стола.
   Раз в год проверяй, что образ открывается.
